# AtCoderの環境とツール

利用候補のツールと役割を整理する。実機での導入状態はここからは確定できない。**このリポジトリは言語別の知識・実践例・コンテスト環境を整理する場所**であり、普段のコンテスト作業ディレクトリそのものではない。

## 普段の作業イメージ

```text
atcoder/                     ← 作業ディレクトリの例（ac-test READMEの想定）
├── ac-test/                 ← localhost bridge、Tampermonkeyスクリプトを持つ別リポジトリ
├── abc467/                  ← cargo-competeで作成したコンテスト
│   ├── src/bin/a.rs
│   └── testcases/a.yml
└── abc468/
```

```sh
# 初回のみ: cargo-competeの公式手順で設定
cargo install cargo-compete --locked
cargo compete init  # 実際の対話入力・既存設定に従う。二重初期化しない

# コンテスト用ワークスペースで
cargo compete new abc467
cd abc467
cargo compete test a
cargo compete submit a
```

> 上記は**利用コマンドの参考例**で、現在のPCの `compete.toml` を取得して再現したものではない。設定ファイルや使用中のRust・crateのバージョンは、実機のコンテスト用ワークスペースを正本とする。 `cargo compete init` の引数と対話設定は [公式手順](https://github.com/qryxip/cargo-compete/blob/master/README-ja.md) に合わせる。

### ac-test と cargo-compete の役割分担

1. `ac-test` の配置例は、`ac-test` と `abc467` を同階層にする構成。
2. 別途 `ac-test` を `cargo run --release` で起動し、`ac-test.user.js` を Tampermonkey に登録する。
   - 2026-10-18時点のTampermonkey一覧には `AtCoder → cargo-compete testcase bridge` があるが、`ac-test.user.js` の `@name` は `ac-test`。**同じスクリプトか未確認**のため、二重導入しないよう [一覧の確認事項](Tampermonkey.md#自作ツール-ac-test-との関係) を参照する。
3. AtCoderの問題ページを開くと、表示中の問題文から収集できるサンプルと、対応可能な入力形式のみの境界値/stressケースを、`abc467/testcases/a.yml` に保存する。
4. `cargo compete test a` でサンプルと生成ケースを実行する。

**重要:** `generated-*` のケースは期待出力（`out`）を付けていない。正答判定ではなく、主にpanic、RE、TLEなどを見つけるためのテスト。複雑な入力形式は自動生成の対象外。詳細は [ac-testのREADME](https://github.com/rebuildup/ac-test#readme) を参照。

## AtCoderのRustジャッジとcargo-competeを揃える

**2026-10-31確認：** [AtCoder公式の2025/10言語更新一覧](https://img.atcoder.jp/file/language-update/2025-10/language-list.html)では **Rust 1.89.0**。公式の[インストールスクリプト](https://img.atcoder.jp/file/language-update/2025-10/088-1-82-0_rustc.toml)にある `Cargo.toml` は **edition 2024**、ビルドは `cargo build --release --quiet --offline`。`cargo-compete` のREADMEに残る `1.42.0`／edition 2018／古いライブラリ群は現行ジャッジの設定ではない。

### compete.toml：新規作成・テスト・提出

既存の `compete.toml` の該当キーを**更新**する例（同じテーブルを二重に作らない。他の設定 `test-suite`、`[template]` などは残す）。

```toml
[template.new]
edition = "2024"
# 依存クレートを使う場合だけ、この値も現在の公式一覧に合わせる:
# dependencies = '''
# proconio = "=0.5.0"
# itertools = "=0.14.0"
# '''

[test]
toolchain = "1.89.0"
# ジャッジ相当の実行性能を確認するときだけ有効化。省略時は dev。
# profile = "release"

[submit]
kind = "file"
path = "{{ src_path }}"
language_id = "6088"
```

- **`[test] toolchain` がテスト時のRustバージョン**。`[build] toolchain` ではない。`rustup run 1.42.0 cargo build ...` と表示された場合はここを確認する。
- **`[template.new] edition` と `dependencies` は、`cargo compete new` でこれから作るパッケージ向け**。既存パッケージの `Cargo.toml` は自動で更新されない。
- **`[submit] language_id` は提出先サイトの選択肢のID**。Rust 1.89.0 は現在 `6088` として案内されているが、次の言語更新時には変わるため、提出画面で確認する。`submit` の `kind` や `path` は既存ワークフローに合わせて維持する。
- `[template.new] dependencies` はTOML文字列の中に依存の記述を書く。**使わないクレートを無理に追加する必要はない**。すでに設定済みなら重複させず更新する。公式の全リストとバージョンは上記インストールスクリプトを参照。

### Cargo.toml：各コンテストのパッケージ

`cargo-compete` が生成した `Cargo.toml` の `[package]` と `[dependencies]` の例。`name` はそのコンテストの実際の名前を使用し、`[package.metadata.cargo-compete.bin]` や `[[bin]]` は**既存の自動生成内容を保持**する。

```toml
[package]
name = "abc440"
version = "0.1.0"
edition = "2024"

[dependencies]
# 利用するときだけ。AtCoderの現在の対応バージョンを固定する。
# proconio = "=0.5.0"
# itertools = "=0.14.0"
```

- `edition` はRustの構文・解釈の設定で、コンパイラ版の切替ではない。**Rust自体は `[test] toolchain`／`rustup` 側で選ぶ**。
- `read<T>()` だけを使う標準テンプレートなら依存クレートの追加は不要。クレートを使う場合、ジャッジで使えるバージョン・機能・依存解決を合わせ、生成済みの `Cargo.lock` も整合させる。
- ローカルの `cargo build` が通っても、ジャッジの `--offline` で解決できない依存は使えない。公式のインストールスクリプトが正本。

### 変更と確認

```powershell
rustup toolchain install 1.89.0
rustup run 1.89.0 rustc --version
cargo compete test c
```

`cargo compete test c` のビルドログが `rustup run 1.89.0 cargo build ...` を使用するか確認する。既存コンテストはその `Cargo.toml` の `edition` も別途見る。Rust 1.58以降では `println!("{ans}")` の変数名キャプチャ構文が使えるため、Rust 1.42の `there is no argument named 'ans'` も解消する。

## 入力の3方式

**標準は提出テンプレートの `read<T>()`。** 空白区切りで1トークンずつ読むため、整数・配列・グラフの入力も、改行に依存せず処理できる。[入出力](../rust/基礎/入出力.md)を正本とする。

```rust
let n: usize = read();
let a: Vec<i64> = (0..n).map(|_| read()).collect();
let s: String = read();
```

| 方式 | 選ぶ場合 | 前提・注意 |
| --- | --- | --- |
| **`read<T>()`（標準）** | 通常の整数・ASCII文字列・空白区切りの配列 | [署名付きテンプレート](../rust/template.rs)に組み込み済み。UTF-8の非ASCII文字列には非対応。大量入力では遅くなる場合がある |
| `proconio::input!` | `Usize1` やネストした配列など、マクロの記法を使いたい | **問題用Cargo.tomlに依存がある環境のみ**。[例](../rust/templates/proconio.rs)。標準テンプレートへの単純追加では依存は自動的に入らない |
| [汎用Scanner](../rust/templates/abc.rs) | クレートが使えず、入力が多い・非ASCIIの文字列を適切に扱いたい | 標準ライブラリのみ。入力関数・`main()`を丸ごと重複させず、どちらかの方式を選ぶ |

### 旧来の行単位入力は互換用

`read_i()`・`read_vi()`・`read_s()` は旧コードのためにスニペットとして残す。**新規の標準ではない**。`read_vi()` は1行だけを読み、配列が改行をまたぐ入力には向かない。`read<T>()` と行単位関数を同時に使うと、読み取り境界が分かりにくくなるため混在させない。

- [旧方式の1行入力例](../rust/templates/line_input.rs)
- [スニペットの定義と互換用接頭辞](../rust/スニペット.md)
- [現在の入力・出力の詳細](../rust/基礎/入出力.md)

`cargo-compete` はコンテスト作成・テスト・提出、`ac-test` はサンプルや境界値ケースの補助。**いずれも入力方式とは独立**している。
