# Rustの開発環境・コンテスト作業

現在使用しているツールと役割を記録する。**このリポジトリはライブラリ・スニペット・学習メモの保管場所**であり、普段のコンテスト作業ディレクトリそのものではない。

## 使用するもの

| ツール | 役割 | 詳細 |
| --- | --- | --- |
| Rust / Cargo | コードのビルド、Rustライブラリのテスト | [Rust公式](https://www.rust-lang.org/tools/install) |
| [cargo-compete](https://github.com/qryxip/cargo-compete) | コンテストごとの作業フォルダ作成、サンプルテスト、提出 | [日本語README](https://github.com/qryxip/cargo-compete/blob/master/README-ja.md) |
| [ac-test（自作）](https://github.com/rebuildup/ac-test) | 問題ページのサンプル取得と、対応可能な問題の境界値・stress入力の追加 | [自作ツールのREADME](https://github.com/rebuildup/ac-test#readme) |
| Tampermonkey | AtCoderの画面表示補助やテストケース連携のUserscript管理 | [現在のインストール一覧（14件）](Tampermonkeyスクリプト.md) |

## 普段の作業イメージ

```text
atcoder/                     ← 作業ディレクトリの例（ac-test READMEの想定）
├── ac-test/                 ← localhost bridge、Tampermonkeyスクリプトを持つ別リポジトリ
├── abc467/                  ← cargo-competeで作成したコンテスト
│   ├── src/bin/a.rs
│   └── testcases/a.yml
└── abc468/
```

```sh
# 初回のみ: cargo-competeの公式手順で設定
cargo install cargo-compete --locked
cargo compete init  # 実際の対話入力・既存設定に従う。二重初期化しない

# コンテスト用ワークスペースで
cargo compete new abc467
cd abc467
cargo compete test a
cargo compete submit a
```

> 上記は**利用コマンドの参考例**で、現在のPCの `compete.toml` を取得して再現したものではない。設定ファイルや使用中のRust・crateのバージョンは、実機のコンテスト用ワークスペースを正本とする。 `cargo compete init` の引数と対話設定は [公式手順](https://github.com/qryxip/cargo-compete/blob/master/README-ja.md) に合わせる。

### ac-test と cargo-compete の役割分担

1. `ac-test` の配置例は、`ac-test` と `abc467` を同階層にする構成。
2. 別途 `ac-test` を `cargo run --release` で起動し、`ac-test.user.js` を Tampermonkey に登録する。
   - 現在のTampermonkey一覧には `AtCoder → cargo-compete testcase bridge` があるが、`ac-test.user.js` の `@name` は `ac-test`。**同じスクリプトか未確認**のため、二重導入しないよう [一覧の確認事項](Tampermonkeyスクリプト.md#自作ツール-ac-test-との関係) を参照する。
3. AtCoderの問題ページを開くと、表示中の問題文から収集できるサンプルと、対応可能な入力形式のみの境界値/stressケースを、`abc467/testcases/a.yml` に保存する。
4. `cargo compete test a` でサンプルと生成ケースを実行する。

**重要:** `generated-*` のケースは期待出力（`out`）を付けていない。正答判定ではなく、主にpanic、RE、TLEなどを見つけるためのテスト。複雑な入力形式は自動生成の対象外。詳細は [ac-testのREADME](https://github.com/rebuildup/ac-test#readme) を参照。

## 入力の3方式

**入力の複雑さと提出先の環境に応じて選ぶ。どれか一つに統一しない。**

| 方式 | 選ぶ状況 | コード例 | 前提・注意 |
| --- | --- | --- | --- |
| **1. 行単位の自作スニペット** | 1行の整数・文字列・短い整数配列 | [line_input.rs](../rust/templates/line_input.rs) / [rust.json](../rust/snippets/rust.json) | `read_vi()` 等は**1行だけ**読む。複数行をまたぐ配列は不得意 |
| **2. proconio** | AtCoderの配列、タプル、グラフ、グリッドなど | [proconio.rs](../rust/templates/proconio.rs) | `cargo-compete` の問題側 `Cargo.toml` に `proconio` が必要 |
| **3. 汎用Scanner** | AtCoder以外、外部クレート不可、改行位置に依存したくないとき | [abc.rs](../rust/templates/abc.rs) | 外部クレート不要。型宣言やループで構造を組み立てる |

### 1. 単純なら既存の1行スニペット

エディタの `stdrvi` から `read_vi()` を展開した場合:

```rust
// 入力例: 10 20 30
let a = read_vi();
let sum: i64 = a.iter().sum();
println!("{sum}");
```

`read_s()`、`read_i()`、`read_vi()` など**現在のスニペットの使い方は変更しない**。
[そのまま使えるコード例](../rust/templates/line_input.rs) も用意した。

注意: `read_vi()` は呼び出すたびに**次の1行**を読み取る。入力が例えば `N` の次に `N` 個の整数として与えられても、整数が改行をまたぐなら一度の `read_vi()` では全部読めない。また、`read_s()` は行の前後の空白を削除する。

### 2. AtCoderで複雑ならproconio

```rust
use proconio::{input, marker::Usize1};

fn main() {
    input! {
        n: usize,
        m: usize,
        edges: [(Usize1, Usize1); m],
    }
    // 頂点番号は入力時に1-indexedから0-indexedへ変換
    let _ = (n, edges);
}
```

`input!` は行ではなくトークンと型を指定して読み取る。配列長・タプル・`Usize1` などがある入力なら、逐次行パースより短くなりやすい。

`proconio` 自体はAtCoder専用ではない。他のCargoプロジェクトでも依存に追加すれば使える。ただし**各オンラインジャッジの提出環境がクレートを利用可能かどうかは別**。 `cargo-compete` だけで自動的にすべてのクレートが利用可能になるわけではない。

### 3. クレートなしで複数行を扱うならScanner

[従来の `abc.rs`](../rust/templates/abc.rs) にある `Scanner` を使う。

```rust
let mut sc = Scanner::new();
let n: usize = sc.next();
let a: Vec<i64> = (0..n).map(|_| sc.next()).collect();
```

`next::<T>()` は空白区切りで読み進めるため、配列の途中で改行されても処理できる。グラフ入力も `(0..m).map(|_| (sc.next::<usize>(), sc.next::<usize>()))` のように読み込める。ただし `Usize1` のような型による添字変換は自分で行う。

比較例: どちらの方式でも、この入力を読み取れる。

```text
5
10 20
30
40 50
```

`proconio` の `a: [i64; 5]` と、Scannerの `(0..5).map(|_| sc.next()).collect::<Vec<i64>>()` は、ともに5個の整数を取得できる。対して既存の `read_vi()` を1回呼ぶだけでは、最初の `10 20` しか得られない。

### コンテスト環境との関係

- `cargo-compete` はコンテストフォルダの作成・テスト・提出を担当し、入力手法とは独立。
- `ac-test` はサンプルと生成テストケースを管理し、同じく3方式のどれとも組み合わせられる。
- **Scannerの正本は** [rust/templates/abc.rs](../rust/templates/abc.rs)。歴史的に `abc.rs` という名前だがAtCoder専用ではない。
- `atcoder-kit` 自体の `cargo test` は、このリポジトリのライブラリ関数のテスト。コンテスト提出の `cargo compete test` とは異なる。

## コンテスト開催中の注意

生成AIによるコード補完・デバッグ・解法の相談は ABC / ARC / AGC の開催中は禁止。使用済みコードの出典管理も必要。詳細は [AtCoderで使うときの注意](AtCoderで使うときの注意.md) と公式ルールを参照。
